The installer that ran is the release asset `install.sh` from `https://github.com/Jabbslad/kiln/releases/download/v0.4.9/install.sh`, checked with `install.sh.sha256` before it was executed. No app source on the host was edited. `deploy/enroll-dark-forge.sh` was not run. Public tcp/8443 was left open. `authorized_keys` was not edited.

`kiln login` from off the host was not attempted. **pending: Jamie off-host test.**

## Installer and kiln-identity

The published `install.sh` was read before it ran. Its sha256 is `f000d5afa9a20955d710aa03c2055645fea6f100a9e665ee9efc71d951ec9c30` and `sha256sum -c` printed `install.sh: OK`. `version=0.4.9`. The bootstrap does not mention `kiln-identity` or `kiln-identity-proxy`. On a host that already has `/etc/kiln`, `/opt/kiln`, or `/var/lib/kiln` it downloads the pinned server archive and runs that archive's `install.sh --apply`.

The server archive sha256 pinned by that script, and matched by the downloaded file, is `c5685705b0eb2367aa90a42288c8e6c47e7dda6971b77e9ec93fb293d356b2db`. The inner `install.sh` was extracted and read before the host install. `binary_names` is `kiln`, `kiln-runtime`, `kiln-network`, `kiln-host`, and `kiln-api`. `upgrade_swap` stops and starts only `kiln-api.service` and `kiln-host.service`. It does not replace, upgrade, or restart `kiln-identity`, `kiln-identity-proxy`, or their units. No skip flag was required.

## What the door runbook changed

`docs/runbooks/2026-10-19-door-public-cert.md` is the merged #27 procedure. Lines in that file that say 0.4.7 were treated as v0.4.9. The installed `kiln-door.service` was left as it was. The new `kiln-api` door command defaults `--session-dir` to `/var/lib/kiln-api/dashboard-session`. That directory did not exist before the rebind. After `kiln-door.service` started at `Tue 2026-10-20 10:06:14 CEST` it exists, mode `700`, owner `kiln-api`. The process command line is the previous unit's arguments plus the new listen address `127.0.0.1:8444`. It does not pass `--session-dir` explicitly; the binary default is that path, and the directory was created by this start.

`/etc/kiln/ca.crt` was not visible in the Caddy container. A read-only bind via `nsenter` failed because `/proc/mounts` and `/proc/self/fd` are not usable in that mount namespace (`mount-exit:1`, then `bind -1 errno 2`). The failed attempt left an empty file (sha256 `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`). That empty file was replaced with `docker cp /etc/kiln/ca.crt caddy:/etc/kiln/ca.crt` and `chmod 444` before `caddy reload`. The container hash then matched the host file and the database row: `f7bb4b2cb0e335047a536b2aeb11eac9489e2d4db87ecc067fdf652dbd8406bf`. Only `ca.crt` was copied. `ca.key`, `door.key`, and `directory.token` were not. Caddy was not restarted: container pid stayed `1302766`, started `2026-09-05T00:20:11.922786918Z`. The copy lives in the container writable layer. Recreating the `caddy` container would drop it, and the port-443 proxy would fail TLS until `ca.crt` is copied again. This deploy did not recreate the container.

`caddy validate` printed `Valid configuration` and a deprecation warning for `tls_trusted_ca_certs`. The runbook block was kept as written. `caddy reload` exited 0. `https://dark-forge.dev/login` still contained `Light the way in.`

The directory PUT returned HTTP 204. Header and JSON files were removed with `shred -u`. The origin column is `https://cli.dark-forge.dev`. The `ca_pem` hash is unchanged.

## Rollback copies

`/opt/kiln/upgrades/0.4.4-8DDh4B` and `/opt/kiln/upgrades/0.4.5-RSNr4F` were already on the host. They were not deleted. `/opt/kiln/upgrades/0.4.6-3vO6d0` is the previous-binary directory this `install.sh --apply` wrote.

Keep `0.4.6-3vO6d0` until the off-host `kiln login` / list / create / exec / delete on port 443 has passed and the operator accepts that v0.4.9 will not be rolled back. That directory is the rollback target for this deploy. `0.4.4-8DDh4B` can be pruned once a return to 0.4.4 is no longer required. `0.4.5-RSNr4F` can be pruned once a return to 0.4.5 is no longer required. Neither older directory is the rollback target for v0.4.9. This deploy did not prune any of them.
